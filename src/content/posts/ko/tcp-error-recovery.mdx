## 2&#46;<strong> 흐름제어</strong>

<p id="411ca4f7-3e01-48fc-ab70-c2e1d94faf45">흐름제어는 <strong>송신자가 수신자에게 처리하지 못할 만큼의 많은 데이터를 전송하는 것을 미리 방지</strong>하는 메커니즘이다&#46; 수신자가 데이터를 받지 못하는 경우는 보통 수신자가 다른 데이터를 처리하고 있거나, 밀려있는 데이터가 많거나 버퍼공간을 충분히 지정해주지 않는 경우다&#46; 이러한 문제를 해결하기 위해 양쪽의 TCP 커넥션이 각각 <span className="notion-color-red"><strong>자신의 receive window(rwnd)를 통지</strong></span>하여 수신데이터를 저장할 버퍼 공간의 크기를 서로에게 알려준다&#46; 이 버퍼 공간은 데이터 처리를 기다리는 응용 계층 프로토콜에 스택을 꽉 채울때까지 데이터가 임시적으로 저장되는 공간이다&#46; 따라서 전송 호스트는 한 번에 window size 필드에 명시된 데이터 양 만큼만 보낼 수 있다&#46;</p>

<p id="d40af087-8a27-4de2-8b10-ed6fd742c0e9">window size를 조정하는 프로세스는 매우 명확하지만, 완벽한 것은 아니다&#46; 데이터가 TCP 스택에 수신될 때마다 ACK가 생성되고 반복적으로 보내지지지만 수신자의 버퍼에 있는 데이터가 항상 즉시 처리되는 것은 아니기 때문이다&#46; window size를 재조정하는 프로세스로 zero window 전송을 통한 데이트 흐름을 중지하는 방법과 TCP sliding window 등의 두가지 방법을 사용한다&#46;</p>

## 3&#46;<strong> 혼잡제어</strong>

<p id="4185bcd4-8a73-4ce1-9173-2547f5f16fca">혼잡붕괴(Congestion collapse)란, <span className="notion-color-red"><strong>Speed mismatch</strong></span>(1G input port 1개에서 100Mbps output port 1개로 나갈 때)거나 여러 port에서 입력된 트래픽이 <span className="notion-color-red"><strong>하나의 port로 집중</strong></span>(1G input port 2개에서 1개의 1G output port으로 나갈 때)되는 등의 상황에 발생한다&#46; 전자의 경우 buffering은 output port의 buffer(output queue)에서 발생하며, 후자의 경우엔 input/output queue 모두 발생할 수 있다&#46; 후자의 경우 port별 경쟁 상황이 발생하는데 queue의 크기가 작으면 buffer overflow에 의해 packet drop이 발생하여 TCP 송신자가 <strong>DUP&#95;ACK를 연속 3회 수신</strong>하게 된다&#46; 반면, queue의 크기가 크면 queue에서 대기하는 buffering delay가 증가하여 <strong>TCP retransmission timeout</strong>이 발생한다&#46; 그리고 이 두 경우에 TCP congestion을 감지하고 혼잡 제어 동작을 수행한다&#46;</p>

<details id="23d2c776-182d-4092-adbe-e65ee4f9cc2f" className="notion-toggle" open>

<summary><strong>TCP retransmission</strong></summary>

<p id="e85f451f-54d3-46c1-854d-e7057b823dcc">호스트가 패킷을 재전송하는 기능은 TCP가 제공하는 가장 기초적인 오류 복구 기능이며, 패킷 손실을 방지하게 설계돼 있다&#46; 패킷 손실은 애플리케이션 오작동, 라우터의 과부하 트래픽, 일시적인 서비스 정지 같은 여러가지 상황에서 발생할 수 있다&#46; 패킷 재전송 여부에 대한 주요 메커니즘은 재전송 타임아웃(RTO, Retransmission Timeout)값을 갖는 재전송 타이머를 이용하는 방법이다&#46; 패킷이 TCP를 이용해 재전송될 때마다 재전송 타이머가 동작하고, 정상적으로 ACK 패킷을 받으면 정지한다&#46; 이 때 패킷 전송과 ACK 패킷 수신 사이의 시간을 왕복 시간(RTT, Round-Trip Time)이라고 하며, RTO는 평활화한 RTT(SRTT)와 RTT 변동(RTTVAR)을 함께 반영하여 계산한다&#46; 재전송 타임아웃이 반복되면 RTO를 두 배로 늘린다&#46; 최대 재전송 시도 수는 송신 운영체제의 설정에 따라 다르지만, 기본적으로 윈도우는 최대 5회, 리눅스는 15회가 디폴트 값으로 설정할 수 있다&#46;</p>

</details>

### <strong>1) Slow Start</strong>

<p id="8d6b3f64-484b-4229-967c-8958bc0c931c">클라이언트와 서버간의 허용량을 가늠하는 유일한 방법은 실제로 데이터를 교환하면서 허용량을 측정하는 것 뿐이다&#46; 이것이 Slow Start가 하는 일이다&#46; 우선 서버가 각 TCP 커넥션마다 새 혼잡윈도(cwnd)를 만들고 그 값을 시스템에서 정해진 안전한 수치로 설정한다&#46; </p>

<details id="e026a311-0f80-4866-928a-dad109a4a334" className="notion-toggle" open>

<summary><strong>cwnd</strong></summary>

<p id="285026c9-f6e1-478b-aee8-024360cf270f">클라이언트로부터 응답확인(ack) 신호를 받기 전에 송신자 측에서 지정하는 최대 송신 데이터량을 의미한다&#46;</p>

<p id="7b468263-cc24-4131-b1f6-22c099adec0f">cwnd는 송신자와 수신자 간에 값이 교환되거나 서로 통지되지 않는다&#46; 송신자와 수신자 사이에서 이동중인 데이터의 최대치는 rwnd와 cwnd 값 중 작은 값이 된다&#46; 최적의 cwnd값을 알아내는 방법은 (매 커넥션마다 수동으로 조정하지는 않고,) ACK 패킷을 받으면서 점점 윈도 사이즈를 늘려간다&#46;</p>

<p id="754d1849-e5d6-4d42-ab8d-b0b63bf345ca">cwnd size는 항상 2의 배수로 증가하는 것은 아니라 maximum sender mss 크기 1만큼 증가한다&#46; (<a href="https://tools.ietf.org/html/rfc5681">https&#58;//tools&#46;ietf&#46;org/html/rfc5681</a><a href="https://lwn.net/Articles/427104/">https&#58;//lwn&#46;net/Articles/427104/</a>,"During slow start, a TCP increments cwnd by at most SMSS bytes for each ACK received that cumulatively acknowledges new data")</p>

</details>

<p id="53917f71-0b92-45fc-837f-6c087d9030d9">혼잡 윈도 크기를 증가시키는데 걸리는 시간을 단축시키기 위해서는 클라이언트와 서버간의 왕복시간을 줄이거나 초기 혼잡윈도크기 값(intial cwnd)을 늘릴 수도 있다&#46; (최근의 리눅스커널은 initial cwnd size를 10 segment (lw 10)로 설정되어 있다&#46; <a href="https://tools.ietf.org/html/rfc6928">https&#58;//tools&#46;ietf&#46;org/html/rfc6928</a>)</p>

### <strong>2) Congestion Avoidance</strong>

<p id="dc04c660-f4d6-49ea-b995-c92af09b7901">혼잡 회피에서 암묵적으로 판단하기에 패킷 손실이 일어났다는 것은 네트워크 혼잡이 일어났다는 신호다&#46; 이동 경로의 어딘가에서 정체가 일어난 링크나 라우터가 패킷을 누락시켰을 것이다&#46; 그래서 네트워크에 부담을 덜어주고 더 이상의 패킷 손실을 막기 위해 윈도 사이즈를 조정해야 하는 것이다&#46;</p>

<p id="1844dbdc-e426-4e34-8724-7631b2a802e5">Packet loss가 감지되면, 바로 이전 Congestion window size를 ssthresh 값으로 설정하고 이후에 congestion avoidance 단계에서 그 ssthresh 값으로부터 segment를 하나씩 증가시키면서 network congestion이 발생하는 지점을 찾는다&#46; packet loss가 발생하면 다시 ssthresh 값을 직전 cwnd의 절반으로 줄이고 다시 slow start를 수행한다&#46; (&lt;그림1&gt;을 참조하자)</p>

<p id="e391531a-3e5a-4288-a8e6-a9aeaabe3eb6">그런데 packet loss가 발생했을 경우 이전까지 TCP 송신자는 매번 retransmission timeout(RTO)가 발생할 때까지 기다려서 packet loss를 감지하였다&#46; 이에 대한 대안으로 Fast Retransmission과  Fast Recovery가 제시되었다&#46;</p>

<hr id="490ed16e-0b94-4aea-a964-b38f2c399107" />

### <strong>3) Fast Retransmission &amp; Fast Recovery</strong>

<p id="602a3cd6-7a3b-4d1e-b52d-5f192fc867b3">Network에서 packet loass가 발생한 사실을 RTO가 아닌 연속 3회 DUP&#95;ACK로 인지하게 될 경우 (&lt;그림1&gt;의 4번, Fast Retransmission) 이전처럼 cwnd를 초기값부터 다시 slow start를 하지 않고 현재의 절반으로 줄인 후에 congestion avoidance를 수행해서 빠르게 packet loss가 발생했던 cwnd 직전까지 찾아간다(Fast recovery)&#46;</p>

<details id="df0aedd3-9550-4c96-829b-797a6567d12a" className="notion-toggle" open>

<summary>중복 ACK (DUP&#95;ACK)</summary>
