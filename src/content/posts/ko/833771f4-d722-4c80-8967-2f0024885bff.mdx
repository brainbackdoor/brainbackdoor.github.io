## 2&#46; <strong>Why not RDBMS?</strong>

<p id="83b1a553-ce7f-4d1c-9837-5277c4aacb25">IT 환경이 고도화되어 처리할 데이터가 수백억건으로 증가함에 따라, 기존의 단일 소프트웨어로는 의미있는 정보를 검색/시각화/예측/분석 등을 하기에 어려움이 있다&#46; DB 쿼리 성능의 주요 제약사항 중 하나는 <strong>쿼리의 순차적인 실행</strong>이다&#46; 대부분의 DB는 다수의 프로세서를 사용할 수 있지만, 하나의 쿼리를 위해 다수의 프로세서를 사용하지는 않는다&#46; 다수의 쿼리를 한번에 수행하기 위해 (batch 등)병렬성을 활용하기는 한다&#46; 하나의 쿼리를 병렬로 실행한다고 해도 DB 성능은 디스크 I/O속도에 의해 여전히 제한될 수 있다&#46; 그리고 기존의 RDBMS를 Distributed Architecutre로 구성할 경우, ACID를 위해 복잡한 locking 방식과 복제 방식을 사용할 수 밖에 없다&#46;</p>

</figure>

<p id="2bc572d5-1b7b-4376-80c9-df83f290fb29">이에 OLAP(Online Analytical Processing), 텍스트 처리, 스트림 처리, 고차원 데이터 처리 등에 있어 특화된 아키텍처로 여러 방법론이 소개되었다&#46; 다만, 데이터를 여러 노드에 나눠 처리한 후 결합하는 경우에도(Distributed Data Parallelism), 네트워크상의 오버헤드가 발생할 수 있다&#46; 따라서 단일 머신에서도 처리할 수 있는 데이터셋을 다룰 때는 비효율적일 수 있으며, 대량의 원자성 트랜잭션을 빠르게 처리해야 하는 OLTP 작업에는 적합하지 않다&#46;</p>

## 3&#46; Why not MapReduce?

<p id="b3d3e40e-b955-46b0-96c0-c8e6a73c871a">과거 구글은 MapReduce를 통해 빅데이터 관련 이슈를 해결하였다&#46; MapReduce란, 문제를 쉽게 병렬화할 수 있게 나눈 후, 장비 클러스터 전체에서 이들을 조정하는 계산 패러다임이다&#46; Hadoop은 분석을 병렬로 수행할 수 있도록 나눠주며, HDFS는 많은 디스크에 흩어져 있는 데이터를 병렬로 읽는다&#46;</p>

<figure id="b4b66532-816c-4aea-b191-5eebaf0e3dfb" className="notion-figure">

<img src="/content/833771f4-d722-4c80-8967-2f0024885bff/b4b66532-816c-4aea-b191-5eebaf0e3dfb.webp" alt="" loading="lazy" width="1638" height="1306" />

</figure>

<p id="9d689001-653b-4935-9e98-30ba56a1e0d7">MapReduce 잡의 결과를 다른 잡에서 사용하려면 HDFS에 저장해야 한다&#46; 메모리는 디스크에 비해 100배 빠르며 네트워크 통신에 비해 일반적으로 100만배 빠르다&#46;</p>

## 4&#46; What's Spark's advantages?

<p id="b97b8204-14f0-4bc0-8e77-4a43bb858504">Hadoop이 HDFS + MapReduce 처리 엔진으로 구성된데 반해, Spark는 대량의 데이터를 메모리에 유지하는 독창적인 설계로 계산 성능을 대폭 끌어올렸다&#46; 따라서 Spark는 Hadoop MapReduce보다 10&#126;100배 빠른 속도로 같은 작업을 수행한다&#46;</p>

<p id="14325cb4-b9a4-40a0-835c-33544069badc">Spark는 여러 데이터 소스에서 읽을 경우<span className="notion-color-blue"> </span><span className="notion-color-blue"><a href="https://spark.apache.org/docs/latest/rdd-programming-guide.html#rdd-persistence"><strong>persist(), cache()</strong></a></span>를 사용하며, Functional Programming 개념을 가져와서 Latency 문제를 해결하였다&#46; 그리고 데이터를 In-memory에 유지하며 Immutable하기에, Functional transformation을 replaying해줌으로써 Fault tolerance를 확보할 수 있다&#46;</p>

<p id="f70653b4-d9fa-4f33-9ef4-91352f5bff9c">또한 <span className="notion-color-blue"><a href="http://knight76.tistory.com/entry/%ED%8E%8C-lazy-evaluation%EB%8A%90%EA%B8%8B%ED%95%9C-%EA%B3%84%EC%82%B0%EB%B2%95%EC%97%90-%EB%8C%80%ED%95%9C-%EC%A2%8B%EC%9D%80-%EC%84%A4%EB%AA%85-%EA%B7%B8%EB%A6%BC-%EC%9E%90%EB%A3%8C"><strong>Lazy execution</strong></a></span>을 통해 네트워크 병목현상을 피할 수 있다&#46; Eager execution은 바로 실행되는데 반해, Lazy execution은<span className="notion-color-blue"> </span><span className="notion-color-blue"><a href="https://spark.apache.org/docs/latest/rdd-programming-guide.html#actions"><strong>Action</strong></a></span>을 호출하기 전까지는<span className="notion-color-blue"> </span><span className="notion-color-blue"><a href="https://spark.apache.org/docs/latest/rdd-programming-guide.html#transformations"><strong>Transformation</strong></a></span>의 계산을 실제로 실행하지 않는다&#46; RDD에 Action이 호출되면 Spark는 해당 RDD 계보를 살펴보고, 이를 바탕으로 연산 그래프를 작성하여 Action을 계산한다&#46; 따라서 빈번한 반복 연산이 이루어질 경우 마지막에 메모리에 올려 계산하여 값을 작성함으로써 IO를 줄일 수 있으며, 조건 검색 혹은 count() 등의 경우에서 Full-scan 비용을 줄일 수 있다&#46;</p>

<span id="b6439c16-494e-463d-8afd-e202b7384ca5"></span>

```kotlin
val largeList: List[String] = ...
val wordsRdd = sc.paralleize(largeList)
val lengthsRdd = wordsRdd.map(_.length) -> lazy하기 때문에 아직 아무 작업도 안함
val totalChars = lengthsRdd.reduce() -> 이때 실행이 됨.
```
