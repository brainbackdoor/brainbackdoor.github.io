## 1&#46; TIME&#95;WAIT 소켓의 문제점과 대안

<p id="9ea25906-0297-4e0a-9e1b-97c9b92126ea">패킷 유실에 따른 비정상적인 통신흐름이 발생할 수 있다&#46; 가령, 아래 그림과 같이 마지막 ACK가 중간에 유실될 경우 FIN에 대한 ACK를 받지 못했기에 LAST-ACK상태이고, SYN 요청에 대해 RST를 보낸다&#46;</p>

<p id="8b7b566b-fc57-4ed6-88f6-0212a263ac5b">반면, TIME&#95;WAIT이 있을 경우에는 수동 종료 측이 재전송한 FIN 패킷을 받고 ACK를 다시 보낸다&#46; FIN을 다시 받은 능동 종료 측은 2MSL 타이머를 재시작한다&#46;</p>

<p id="f59d4dd9-f211-4f87-8e2a-7dc13cbb9fa4">active closer(먼저 연결을 끊는) 쪽에서 TIME&#95;WAIT 소켓이 생성된다&#46; </p>

<figure id="65350709-7bf6-4b84-94ea-e4e6d71f2d6e" className="notion-bookmark">

<p><a href="https://docs.likejazz.com/time-wait/">TIME&#95;WAIT 상태란 무엇인가</a></p><p>TIME&#95;WAIT 상태가 늘어나면 서버의 소켓이 고갈되어 커넥션 타임아웃이 발생한다는 얘기를 한다&#46; 이 말이 올바른 얘기인지, TIME&#95;WAIT은 어떠한 경우에 발생하고 어떤 특징이 있는지 살펴본다&#46; TIME&#95;WAIT 이란 TCP 상태의 가장 마지막 단계이여, 이미 지난 CLOSE&#95;WAIT 문서에서도 살펴본바 있다&#46; Active Close 즉, 먼저 close() 를 요청한 곳에서 최종적으로 남게되며, 2 MSL 동안 유지된다&#46;</p>

</figure>

<p id="886b6003-27fd-4157-bb1b-90a55181caee">TIME&#95;WAIT 소켓이 많아지면, <span className="notion-color-red"><strong>로컬의 포트 고갈에 따른 애플리케이션 타임아웃, 잦은 TCP connection 생성/해제로 인해 서비스의 응답속도가 낮아진다</strong></span><span className="notion-color-red">&#46;</span> (TIME&#95;WAIT 소켓의 기본 타임아웃은 1분이다&#46;)</p>

<span id="b6bac585-02db-4b5b-b14c-0e2272c64aec"></span>

### 1) <strong>클라이언트 입장</strong> 

<p id="944c09a6-d86b-4dc1-9dbd-031e3f10c227">커널 파라미터(<code>tcp&#95;tw&#95;reuse</code>)를 사용하여 TIME&#95;WAIT 소켓을 재사용할 수 있다&#46; 하지만 불필요한 TCP 3way handshake가  일어날 수 있으므로 요청할 때마다 소켓을 새로 연결하는 방식(Connectionless)가 아닌, 미리 <strong>소켓을 열어놓고 처리하는 방식(</strong><span className="notion-color-red"><strong>Connection Pool</strong></span><strong>)</strong>으로 해결할 수 있다&#46;</p>

<span id="76297c88-8a95-4a69-a4fc-ec70251932f4"></span>

### 2) 서버 입장 

<p id="0a0f2e6b-e55f-489d-83e6-426dafe34802">HTTP 연결 재사용은 불필요한 3 way handshake와 연결 종료를 줄일 수 있다&#46; TCP keepalive는 별도 기능으로, SO&#95;KEEPALIVE를 켠 유휴 연결에서 상대의 응답을 확인한다&#46; 보다 구체적으로는, keepalive timeout 시간이 지나면(<code>tcp&#95;keepalive&#95;time</code> 설정값) 서버에서 <strong>Keepalive 확인 패킷</strong>을 보낸다&#46; 이 패킷에 대한 응답을 받으면 타이머는 원래 값으로 돌아가 다시 카운트를 진행한다&#46; 반면  응답을 받지 못한 경우 <code>tcp&#95;keepalive&#95;intvl</code>에 정의된 시간만큼 경과한 후 요청을 다시 보내게 되고, <code>tcp&#95;keepalive&#95;probes</code>에 정의된 횟수만큼 보낸다&#46; 이 후로도 응답이 없을 경우 probe를 보내는 쪽에서 연결 실패를 판정하고 소켓을 정리한다&#46; RST 전송 등 후속 동작은 구현에 따라 다르다&#46; (그리하여 Keepalive를 사용할 경우 연결이 끊어졌음에도 FIN 패킷을 받지 못해 정리되지 않고 남아있던 좀비 커넥션을 없애는 효과도 발생한다&#46;)</p>

## 2&#46; HTTP Keepalive

<p id="834b2b5c-bd14-4654-bbe0-af165587310c">HTTP Keepalive는 설정된 기간까지만 Connection을 유지하다 <strong>FIN</strong>을 서버에서 먼저 날린다&#46; Connection을 유지하기 위해서 클라이언트는 요청에 <code>Connection&#58;Keep-Alive</code> 헤더를 포함시킨다&#46;(HTTP/1&#46;0) HTTP/1&#46;1에서는 해당 설정이 빠졌고, 기본적으로 활성화되어 있다&#46; Connection 종료시에 <code>Connection&#58; close</code>헤더를 명시해야 한다&#46;</p>

<p id="15f31b20-1a74-48ee-8d01-ef6458d86cb6">즉, <span className="notion-color-red"><strong>TCP keepalive는 유휴 TCP 연결에서 상대의 응답을 확인하고, HTTP Keepalive는 같은 연결을 다음 HTTP 요청에도 재사용하는 방식이다&#46; HTTP 서버는 설정한 유휴 제한에 따라 연결을 종료할 수 있다</strong></span><span className="notion-color-red">&#46;</span> 이에 TCP Keepalive는 mq, kafka 등 TCP 기반의 서비스들을 대상으로 지속적 연결을 유지해야 하는 경우 사용되고, HTTP Keepalive는 Apache, Nginx 등 웹 애플리케이션에서 설정된 기간까지 최대한 연결을 유지하기 위해 사용된다&#46; (두 설정을 모두 적용했을 경우 HTTP Keepalive가 능동적으로 FIN 패킷을 보내기에 이 설정대로 동작한다&#46;)</p>

## 3&#46; keep-alive 제한과 규칙

<ul>

<li id="f273648e-dac7-4e0e-8dad-1270330e8939">

<p>클라이언트가 요청에 <code>Connection&#58; close</code> 헤더를 포함해 보냈으면, 그 커넥션으로 추가적인 요청을 보낼 수 없다&#46;</p>

</li>

<li id="52a253c1-bae5-41b7-9add-553bbc357e1a">

<p>메시지가 자신의 길이 정보를 정확히 가지고 있을 때에만 Connection을 지속시킬 수 있다&#46; 예를 들어 Entity body는 Content-Length를 가지거나 chunked transfer encoding으로 인코드되어 있어야 한다&#46;</p>

</li>

<li id="b1bf0681-e153-41f2-8e19-d0a9c1706a47">

<p>HTTP/1&#46;1 프락시는 클라이언트와 서버 각각에 대해 별도의 keepalive connection을 맺고 관리해야 한다&#46;</p>

</li>

</ul>
