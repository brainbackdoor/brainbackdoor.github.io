## 200이 적절하다는 주장

<span id="12b7d008-a1aa-4145-9ad9-a530f0275f6e" data-editorial-omission="reading-w06-heading-repeat" hidden></span>

<p id="eb32b543-132f-459f-b736-348c925f07ee">HTTP에서 이야기하는 resource 라는 개념을 서버 데이터와 엮지 않고 온전히 URI 라고 보아야 한다&#46; 즉, <strong>서버의 데이터 없음을 HTTP resource와 엮지 않아야 한다</strong>는 것으로, 위의 경우에는 <strong>빈값의 200 응답</strong>을 해야 한다는 것이다&#46;</p>

<p id="d4d83fce-6ac3-4125-8a7a-2f54a30c0649">다만, <strong>DELETE 메서드에서 없는 데이터를 삭제하려고 했을 때 이 요청은 400 에러로 처리</strong>하여야 하는데, 이는 서버에서 요청이 수용되었으나 클라이언트의 요청이 잘못되었음을 의미하기 때문이다&#46; 이렇게 리소스와 데이터 자원을 분리하는 이유는 <strong>명확함을 강조</strong>하기 위함이다&#46;</p>

<p id="437c48df-1686-4ac0-bb6c-ea3cc739c1d2">그리고 REST를 지향하는 API에서도, 삭제를 실행 했을 때 그 데이터가 삭제 가능한 상황을 단순하게 데이터가 존재한다고 판단하지 않는다&#46; 그 데이터에 얽혀있는 비지니스적인 요소에 따라 요청 클라이언트에게 데이터가 없다고 밝혀야 할 수도 있고, 삭제가 불가능하다고 밝혀야 할 때도 있다&#46;</p>

<p id="a5689c35-ea41-4c8b-a57c-7f7d7a18de00">가령, 주문을 실행한다고 했을 때 주문이 실행 불가능한 여러가지 경우가 있다&#46; 재고가 떨어져서, 혹은 판매자가 폐업한 경우 등의 상황에서 404, 400, 500 에러는 적절치 않다&#46; 리소스 수용이 정상적으로 이루어졌고, 요청한 데이터에도 이상이 없고(클라이언트에게 책임이 없고), 서버에서 비정상적이고 식별 불가한 에러를 발생한 것도 아니므로 200 응답을 주는 것이 적절해 보인다&#46; 다만 클라이언트에서 식별에 대한 응답을 하기 위해 요청은 성공했지만 주문에는 실패했다는 의미로 내부적으로 관리되는 상태 코드를 응답 body 에 명시하도록 한다&#46; 이러한 사용은 실제 서버에 이상이 있는지, 클라이언트가 잘못된 요청을 하는지에 대한 구분을 명확히 함으로써 장애시 트래킹 포인트를 좁히는데에도 큰 역할을 한다&#46;</p>

<p id="d07962de-7b6d-43cc-a4ae-d344f4d034fc">즉, <span className="notion-color-teal"><strong>조회시 없을 때는 200, PUT/DELETE의 경우 상황에 따라 (데이터가 있어야하는데 없는 경우) 4xx, 아니면 200에 응답 body에 별도로 메시지나 정책적으로 만든 상태코드를 담아서 보내는 것이 적절하다</strong></span>는 주장이다&#46;</p>

<p id="6da62b72-fce2-4dba-87fd-26c5bb02bcf5">위의 주장은 현재 국내 몇 군데 규모있는 회사 개발자들의 의견이었고, 나 역시 그렇게 생각하고 있었다&#46; 그래서 확인차 몇군데 둘러보니 실제로 그렇게 운영되고 있다&#46;</p>

## 400이 적절하다는 주장

<p id="bd78594e-5a89-461e-9a45-81d68597ca06">위의 내용만 보면 200이 타당한 듯 보인다&#46; 하지만 404 의견을 듣고 자료를 찾아보니 이거 역시 만만치가 않다&#46;</p>

<p id="950d1f70-676f-4f43-9715-d43e22ac2697">우선, 404 NOT FOUND가 적절하다는 입장은, <span className="notion-color-blue"><strong><a href="https://tools.ietf.org/html/rfc7231">https&#58;//tools&#46;ietf&#46;org/html/rfc7231</a></strong></span> 에 근거를 두었다&#46;</p>

<p id="75fac94a-8be8-4649-a2ec-3cabe14f1d4c"><strong>200 status code</strong></p>

<blockquote id="bacdbd2a-e6cb-463b-8987-b1dd4e4ef45a">

<p>The 200 (OK) status code indicates that the request has succeeded&#46;<br />The payload sent in a 200 response depends on the request method&#46;<br />GET a representation of the target resource;</p>

</blockquote>

<p id="71dd6d33-7100-4afb-a073-a2f6356df137">200은 요청이 성공했음을 나타내며 페이로드로 해당 resouce의 representation이 응답된다&#46;</p>

<blockquote id="c9e9605f-72a8-4d0e-97f2-7838e73932df">

<p>Aside from responses to CONNECT, a 200 response always has a payload, though an origin server MAY generate a payload body of zero length&#46;<br />If no payload is desired, an origin server ought to send 204 (No Content) instead&#46;</p>

</blockquote>

<p id="b2a15889-ccd5-4ddf-9d5d-b0c10ad06a93">200은 항상 payload를 가지고 있어야 하고 응답이 없는 경우 204를 보내주어야 한다&#46;</p>

<p id="8dfe2b8c-b8d9-4c45-a7a2-b89ae3f70e5b"><strong>204 status code</strong></p>

<blockquote id="a2a2b2fe-e43d-4ace-bae9-1c611f0387a0">

<p>The 204 (No Content) status code indicates that the server has successfully fulfilled the request and that there is no additional content to send in the response payload body&#46;</p>

</blockquote>

<p id="2206f717-3fc7-4402-afcd-137eb43f4a14">204는 요청을 성공적으로 이행하고 응답 페이로드에 추가적으로 보낼 컨텐츠가 없는 경우를 나타낸다&#46;</p>

<blockquote id="5b5543d1-5dfa-42f0-aa95-b3f92aef3c4e">

<p>For example, if a 204 status code is received in response to a PUT request and the response contains an ETag header field, then the PUT was successful and the ETag field-value contains the entity-tag for the new representation of that target resource&#46;</p>

</blockquote>

<p id="c1434ad2-b6ea-4cd9-a8b7-d3cf7ad7d97e">예를 들면, 추가적으로 보낼 컨텐츠가 없는 경우란 PUT 요청을 받고, ETag Header 필드를 포함하여 contents에 보낼 필요가 없을 때를 말한다&#46; 즉, 204 응답은 타겟 리소스에 성공적으로 적용되었음을 나타내며, 암시적으로 useragent가 횡단(접근)할 필요가 없음을 나타낸다&#46;</p>

<p id="fcd78cf5-4a29-4912-a043-439ba88dd1ed"><strong>404 status code</strong></p>

<blockquote id="13f1bdfb-cf53-4aed-bd39-daed201924eb">

<p>The 404 (Not Found) status code indicates that the origin server did not find a current representation for the target resource or is not willing to disclose that one exists&#46;</p>

</blockquote>

<p id="6b142a80-69f6-4512-91bb-8aff83e4a610">404 응답은 서버가 타겟 리소스의 representation을 찾지 못하였거나 존재한다는 것을 드러내려고 하지 않음을 나타낸다&#46;</p>

<p id="0df4c14b-cc67-4072-b06e-bcf1871276dd"><strong>즉, </strong>HTTP 요청의 대상이 리소스임을 생각해 본다면</p>

<p id="0c664e2b-734b-47c7-9d4f-a1b28b112cdc"><span className="notion-color-teal"><strong>The target of an HTTP request is called a "resource"</strong></span></p>

<p id="7a008cff-ac20-4a7b-a085-d1e19bb2cc4b">서버가 정상적으로 동작함의 여부가 아니라 요청한 리소스가 정상적으로 응답이 오는가에 따라서 응답 코드를 판단해야 한다고 생각하다는 것으로, rfc7231문서에 정의된 Response Status Code 중 200과 204 두 상태 코드 모두 <strong>uri가 가리키는 resource가 존재하지 않는 경우</strong>의 상태를 나타내기는 어렵다는 주장이며, 404 상태 코드가 보다 명확하다는 입장이었다&#46;</p>

<figure id="6671cb2f-2a49-4c4a-a2e0-4f5772b80743" className="notion-figure">

<img src="/content/14b691d7-7fd7-4e95-8787-49e06111755f/6671cb2f-2a49-4c4a-a2e0-4f5772b80743.webp" alt="" loading="lazy" width="1399" height="30" />

</figure>

<p id="0dc77bf5-7d06-45e5-9e7d-da5fdb24255c">추가적으로, ResponseEntity 구현체를 보면 Body에 null을 넘겨줄 경우 notFound()를 리턴하도록 정적 팩토리 메서드를 작성했음을 확인할 수 있다&#46;</p>

<span id="58b83f2a-835f-47f1-82f3-59b3685939a0"></span>

```java
public static <T> ResponseEntity<T> of(Optional<T> body) {
        Assert.notNull(body, "Body must not be null");
        return body.map(ResponseEntity::ok).orElse(notFound().build());
}
```

<p id="60b80bc0-916d-4844-b82e-93bcade957a6"><em><strong>"서버가 요청한 URL을 찾을 수 없음을 알려주기 위해 사용한다&#46; 종종, 클라이언트 애플리케이션이 사용자에게 보여주기 위한 엔터티가 포함된다&#46;"</strong></em></p>
