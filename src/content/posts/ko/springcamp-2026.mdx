## Spring I/O 2026 — 변화하는 스프링, 떠오르는 AI, 그리고 우리의 준비

<span id="38190d37-083f-80d2-8ca3-c22940c6004b"></span>

### Virtual Thread

<p id="38190d37-083f-8028-9e81-c9fdec70b1eb">요청 하나에 스레드 하나&#46;</p>

<p id="38190d37-083f-80da-8840-c69f458f79e1">"요청이 몰리면 톰캣이 막힌다"는 말은, 반은 맞고 반은 틀리다&#46; 일단 <strong>커넥션은 수락된다&#46;</strong> 톰캣 8&#46;5+가 NIO로 <code>max-connections</code>(기본 8192)까지 받아 폴링하기 때문이다&#46; 정작 병목은 요청을 <em>처리하는</em> <strong>worker 스레드</strong>에서 생긴다&#46; 기본 <code>max-threads</code>는 200이다&#46; worker 하나가 DB나 외부 API를 기다리는 동안 묶이면, 유휴 스레드가 쌓여 병목이 된다&#46; 그래서 자원을 효율적으로 쓰려고, 아래 공식으로 스레드 수를 잡기도 한다&#46;</p>

<blockquote id="38190d37-083f-8015-81c8-cff89e4f4108">

<p>적절한 스레드 수 = 코어 수 × (1 + 대기시간 / 서비스시간)</p>

</blockquote>

<p id="38190d37-083f-8048-b265-f8832b4f7170">가령 idle이 평균 99%면, 이론상 코어 8개로 worker <strong>800개</strong>를 돌릴 수 있다&#46; 하지만 트랜잭션이 무거우면 대기가 길어져 800개로도 모자라다&#46; 그래서 몇몇 서비스는 WebFlux로 풀기도 했다&#46; 코드를 논블로킹으로 바꿔야 하고 스택 트레이스도 끊기지만, 제한된 서버 자원으로 처리량을 확보하려면 어쩔 수 없었다&#46;</p>

<p id="38190d37-083f-8003-ab00-dfd072c1bd5e">Virtual Thread는 <strong>기다릴 때 스레드를 반납</strong>한다&#46; 그만큼 자원을 효율적으로 쓸 수 있다&#46;</p>

<p id="38190d37-083f-8091-8ea4-fc8e75024454">가상 스레드는 실행될 때만 <strong>carrier 스레드</strong>(기본 <code>ForkJoinPool</code>)에 <strong>mount</strong>한다&#46; 블로킹을 만나면 <strong>unmount</strong>해 OS 스레드를 반납하고, carrier는 다른 가상 스레드를 <strong>mount</strong>한다&#46; 따라서 이론적으로 스레드 <code>대기시간</code>이 사라지는 셈이다&#46; 다만 I/O·DB 대기 자체가 줄어드는 것은 아니고, 기다리는 동안 carrier를 다른 가상 스레드가 쓰는 것이다&#46;</p>

<p id="38190d37-083f-80da-9d4c-c404a7ae3830"><a href="https://www.oracle.com/news/announcement/oracle-releases-java-25-2025-09-16/">JDK 25</a> 이전에는, <code>synchronized</code> 안에서 블로킹하면 carrier를 반납하지 못하고 <strong>고정(pinning)</strong> 되는 이슈로 인해 처리량이 내려갔다&#46; <code>synchronized</code>는 <strong>HikariCP</strong> 등 여러 라이브러리 코드에 포함되어 있기 때문에, 사실상 Virtual Thread의 실익이 크지 않았다&#46; <a href="https://openjdk.org/jeps/491">JEP 491</a>은 모니터 소유권을 carrier가 아니라 Virtual Thread에 연결해 이 문제를 풀었다고 한다&#46; JEP 491은 JDK 24에 처음 반영되었고, LTS로는 JDK 25가 첫 버전이다&#46; 다만 native·foreign 호출 중 등 일부 pinning 경로는 남는다&#46;</p>

<span id="38190d37-083f-8099-97ac-c34773eca0bb"></span>

```text
spring.threads.virtual.enabled=true
```

<p id="38190d37-083f-8097-8559-f62e8fcd6e86">위 설정만 하면 Boot 3&#46;2+, JDK 21+에서 톰캣 요청·<code>&#64;Async</code>·<code>&#64;Scheduled</code>·Kafka·RabbitMQ 리스너가 모두 Virtual Thread로 적용된다&#46; 단, 직접 정의한 Executor 빈이 있으면 &#64;Async 같은 작업 실행은 자동 구성 실행기 대신 그 빈을 쓰므로, 버전별 자동 구성 범위를 확인해야 한다&#46; (데몬이라 <code>&#64;Scheduled</code>만 도는 앱은 <code>spring&#46;main&#46;keep-alive=true</code>도 둬야 JVM이 안 죽는다&#46;)</p>

<p id="38190d37-083f-801a-a904-f4755c1de3fc"><strong>Virtual Thread를 켠다면 아래를 고려해야 한다고 한다&#46;</strong></p>

<ul>

<li id="38190d37-083f-8062-9212-e546f613eacc">

<p><strong>스레드를 풀링하지 않는다&#46;</strong> 가상 스레드는 만들고 버리는 비용이 거의 없기 때문에, 굳이 풀에 모아 재사용할 이유가 없다&#46; 오히려 풀에 가두면 풀 크기가 곧 동시성 상한이 되어, 가상 스레드의 장점이 사라진다&#46; 요청마다 새로 하나씩 쓰면 된다(<code>Executors&#46;newVirtualThreadPerTaskExecutor()</code>)&#46;</p>

</li>

<li id="38190d37-083f-801b-b356-d668dd4f7453">

<p><code><strong>ThreadLocal</strong></code><strong>을 무겁게 쓰지 말자&#46;</strong> 예전엔 스레드가 수백 개라, <code>ThreadLocal</code>에 담은 객체도 많아야 수백개 정도여서 부담이 적었다&#46; 그런데 가상 스레드는 수백만 개라, 스레드마다 들고 있으면 메모리가 급격히 늘 수 있다&#46; 무거운 객체는 공유 불변으로 두거나 Scoped Value로 옮겨야 한다&#46;</p>

</li>

<li id="38190d37-083f-80dd-a7d3-f0851f60bf27">

<p><strong>외부 자원에 상한을 직접 걸어야 한다(백프레셔)&#46;</strong> 예전엔 worker가 200개로 묶여 있어, 한 번에 DB, 외부 API를 호출하는 수를 자연히 제한할 수 있었다&#46; HikariCP 풀은 기본적으로 10이라, 10개만 처리하고 나머지는 대기하므로 한번에 만 개의 요청이 오면 DB에 부하가 몰린다&#46; 그래서 처리량의 한계가 스레드에서 <strong>커넥션 풀, 외부 API 쪽으로 옮겨간다&#46;</strong> 풀은 DB가 감당할 만큼으로 설정하고, 외부 API엔 동시 호출 상한을 직접 걸어야 한다&#46; <code><a href="https://spring.io/blog/2025/09/09/core-spring-resilience-features/">&#64;ConcurrencyLimit</a></code>(Spring Framework 7)을 적용하자&#46;</p>

</li>

</ul>

### 싱글 테넌시에서 멀티 테넌시로, JVM의 강점이 약점이 되다

<p id="38190d37-083f-80cf-89e1-dfc2a62ac805">"강력한 한 대의 머신에서, 소수의 서비스를, 오래 돌린다&#46;"</p>

<p id="38190d37-083f-80dd-8dec-d94a663ab68f">자바는 이 가정 위에서 설계되었다고 한다&#46; JIT는 오래 돌수록 더 최적화하니 기동이 길어도 이득이었다&#46; GC는 메모리를 넉넉히 쓰며 처리량을 끌어올렸고, 리플렉션·동적 로딩·실시간 프로파일링 등 리치 런타임이 개발을 편하게 했다&#46; 모두 서버 한 대를 오래 쓰는 환경에 맞는 선택이었다&#46;</p>

<p id="38190d37-083f-8060-817a-d996c9d1b3c7">그런데 요새는 머신 하나에 컨테이너를 띄워 여러 서비스가 나눠 쓰는 멀티 테넌시 환경이 선호된다&#46; 서버 인스턴스도 통째로 내 것이 아니고, 스케일 인/아웃과 마이그레이션이 수시로 일어난다&#46; 그러자 같은 설계가 거꾸로 발목을 잡았다&#46; 잦은 재기동마다 JIT를 다시 돌려야 하고, 메모리 풋프린트는 오버부킹된 호스트에서 노이지 네이버(한 프로세스가 이웃 몫까지 잡아먹는 현상)를 일으킨다&#46;</p>

<p id="38190d37-083f-80f3-824b-cf1c4556ebfc">게다가 Polyglot 환경, 개발 장비 성능의 개선 등으로 런타임이 하던 일의 일부가 OS 레벨과 빌드 타임으로 내려갔다&#46; 가령 모니터링도 <code>perf</code>·<code>eBPF</code>처럼 언어를 안 가리는 OS 도구를 쓴다&#46; 여러 언어로 개발해야 한다면, 공통적으로 활용할 수 있는 도구가 유리하기 때문이다&#46; 게다가 개발 장비 성능도 좋아져 런타임 JIT 보단, 빌드 타임 AOT 쪽으로 최적화하기도 한다&#46; 이에 한동안 GraalVM Native Image가 대안으로 제시되기도 했지만, 빌드에 상당히 많은 CPU와 메모리가 필요하고, 무료 에디션은 고급 최적화와 GC가 막혀 있고 디버깅도 어려워서 관심이 금세 사그라들었다고 한다&#46; Project Leyden도 좋은 접근이기는 하나 아직은 힌트, 캐시 수준이라, 런타임이 무겁다고 한다&#46;</p>

<p id="38190d37-083f-80c2-b328-def58c672a02">게다가 자바는 컴파일러와 표준 라이브러리만 제공하는 미니멀한 구성이라 빌드, 의존성, IDE가 제각각이고 커뮤니티에 의존적이다&#46; 요새 나오는 언어들은 코드 스타일, 정적분석, 테스팅, 의존성 관리, 빌드 시스템, 개발 환경 통합 등 제공해주는게 많으므로, 이제 셋업하는 스타트업들이 자바를 선택할 유인이 적다고 한다&#46;</p>

<figure id="38190d37-083f-800e-8665-d1ebab240326" className="notion-figure">

<img src="/content/38190d37-083f-8033-a7e8-f3996e11cf55/38190d37-083f-800e-8665-d1ebab240326.webp" alt="" loading="lazy" width="2048" height="955" />

</figure>

<p id="38190d37-083f-80ab-8586-fedaa2afce61">그래서 자바 진영에선 두 가지 접근이 가능하다&#46;</p>

<p id="38190d37-083f-8051-8fc8-e5b0d05f2de9">자바 자체를 고치거나(Amber·Loom·Panama), 아예 JVM 위 새 언어로 떠나거나(Kotlin·Scala)&#46; 하지만 전자는 하위 호환 문제를 해결하기가 어렵다&#46; 가령, Project Valhalla (Value Object)는 2014년에 시작해 2026년에야 첫 프리뷰라고 한다&#46; 그리고 코틀린을 사용한다 하더라도 결국 JVM 환경이니, 무거운 런타임과 상호운용 비용도 발생할 수 있다&#46; (가령, 자바 진영에서 코틀린의 장점을 흡수해 기능이 추가된다면 이 또한 대응해야 한다&#46;)</p>

<p id="38190d37-083f-803c-aa4f-cc5dabc93bd4">추가적으로&#46;&#46; 자바 챔피언인 희승님은 요새, 자바를 잘 사용하지 않는다고 하셨다&#46; <strong>기술 지형은 늘 바뀌므로, 한 언어만 붙들 이유는 없다는 것</strong>이다&#46; 예전엔 팀이 익숙한 기술을 골랐다면, 이제는 AI 덕에 낯선 기술도 고를 수 있으므로 상황에 맞게 선택한다고 하셨다&#46;</p>

## 세션 3 — 정승주&#58; 워크플로우 코드 왜 항상 복잡할까? - Temporal이 보여준 다른 방법

<p id="38190d37-083f-8047-a76f-cba89ca9c00f">발표자는 <strong>고객 보상 워크플로우</strong>(데이터 수집 → 금액 계산 → 매니저 승인 대기 → 크레딧 지급)를 예로, 비즈니스 로직은 단순한데 이걸 <em>완수</em>시키려면 재시도·타임아웃·결과 영속화(수집 단계), 타이머·외부 신호 대기(7일 승인 단계), 원자성·보상(지급 단계) 같은 부가 로직이 도메인 로직에 더 붙어야 한다는 문제를 제기했대&#46; 워크플로우는 코드만 봐선 비즈니스 로직이 눈에 잘 안 들어온다는 거다&#46;</p>

<span id="38190d37-083f-8017-b433-c1c9901a19d2"></span>

### Durable Execution&#58; 실행 그 자체가 상태가 된다

<p id="38190d37-083f-804c-9021-c2f442b23763"><strong>Temporal의 카피는 "실패가 없는 것처럼 코드를 짠다"이다&#46;</strong> 한 번 시작한 워크플로우는 프로세스가 죽어도, 며칠이 걸려도 끝까지 완수된다&#46; 이게 가능한 건 역할이 갈리기 때문이다&#46; Temporal Server는 모든 실행 상태를 보관·조정하되, 코드는 실행하지 않는다&#46; Worker는 반대로 내 코드를 돌리고 결과를 보고하되, 자기 상태는 가지지 않는다&#46; 그래서 Worker가 죽어도 상태는 전부 Temporal Server에 남아, 다른 Worker가 이어받는다&#46;</p>

<ul>

<li id="38190d37-083f-80f5-b89f-c47591380c7f">

<p><strong>① Event History&#46;</strong> 워크플로우에서 일어난 모든 사건(시작/종료, Activity 호출과 결과, 타이머 시작/만료, 외부 신호)을 지우지 않고 기록한다&#46;</p>

</li>

<li id="38190d37-083f-80c1-a89b-f62f171e2ce3">

<p><strong>② Replay&#46;</strong> 워크플로우 코드는 1일 대기, 배포 등 여러 이유로 처음부터 다시 실행될 수 있다&#46; 이 때, 멈춘 자리의 스택, 메모리를 저장, 복원하는 게 아니라, 코드를 처음부터 돌리되 Event History를 입력으로 준다고 한다&#46; 코드가 결정적(deterministic)이면 매번 같은 분기를 타 마지막 기록 지점까지 똑같이 따라잡고, 그 뒤부터 실제로 이어진다&#46; 그래서 워크플로우는 반드시 결정적이어야 한다&#46; Worker가 결과 보고 직전에 죽으면 Activity가 재시도될 수 있어, Activity는 at-least-once를 전제로 멱등하게 설계해야 한다&#46;</p>

</li>

<li id="38190d37-083f-80de-8c3b-e407fb8a6088">

<p><strong>③ Activity Stub&#46;</strong> "히스토리에 있으면 기록된 결과를 쓰고, 없으면 실제로 호출한다"는 분기를 구현한 적이 없는데도 동작하는 건, SDK가 Activity 인터페이스와 같은 시그니처의 <strong>stub</strong>(<code>Workflow&#46;newActivityStub()</code>)을 런타임에 만들어 호출을 가로채 Temporal 명령으로 바꾸기 때문이다&#46; 스프링의 프록시처럼 동작하지만, Temporal 공식 용어는 stub이다&#46;</p>

</li>

</ul>

<p id="38190d37-083f-804b-85c1-ebf02798be64">Activity는 본질적으로 비결정적(랜덤, DB, 부수효과)인데, 워크플로우는 결정적이어야 한다&#46; 이에 Temporal은, Activity를 1회차에만 실제로 실행하고 그 결과를 Event History에 영속화한 뒤, 재실행 때는 부르지 않고 기록된 값을 그대로 돌려준다&#46; <strong>비결정적 Activity를 워크플로우가 결정적으로 호출하는 셈이다&#46;</strong></p>

<p id="38190d37-083f-80d1-9c8a-cf0b9fc9c90a">물론 장점만 있는 건 아니다&#46; Temporal Server 클러스터 운영(또는 클라우드) 비용, 워크플로우의 결정성 제약, 그리고 진행 중인 워크플로우가 Replay로 깨질 수 있어 코드 변경 시 버전 관리가 필요하다&#46; 하지만 대부분 한 번만 치르는 비용이다&#46; 구축해 두면 이후 워크플로우는 같은 기반 위에서 돌릴 수 있다&#46;</p>

<p id="38190d37-083f-805f-8137-dcfc8fd2b060">승주님은 워크플로우가 복잡한 건 문제가 복잡해서가 아니라, 분산 환경이 만든 <strong>우발적 복잡도</strong>를 우리가 비즈니스 코드 안에서 직접 떠안아 왔기 때문이라고 했다&#46; Temporal은 그 우발적 복잡도를 <em>옆 함수나 다른 레이어가 아니라</em> 런타임으로 옮긴다&#46; 덕분에 소스코드에는 비즈니스만 남는다&#46;</p>
