## 1&#46; DataFrame

<figure id="64e71090-1181-4464-80b0-9fee862e6ff1" className="notion-figure">

<img src="/content/c9edaff4-1f8b-48aa-a092-730b932155fb/64e71090-1181-4464-80b0-9fee862e6ff1.webp" alt="" loading="lazy" width="1724" height="1094" />

<p id="e5ff6281-f106-4db3-b5cc-b9002c3373a2">Spark는 데이터를 테이블 형태로 다룰 수 있도록 API를 제공한다&#46; 물리적으로는 여러 머신의 메모리에 분산되어 있더라도, 사용자가 데이터를 마치 하나의 테이블처럼 다룰 수 있다&#46;</p>

<span id="76c0484f-452b-47dd-a57e-e30574c7d737"></span>

```kotlin
df = spark.read.load("[파일경로]",
                     format="csv", 
                     sep="\t", 
                     inferSchema="true", // * 타입 추론
                     header="true")

dfSelected = df.select(
    col("ID").alias("id"),
    col("Year_Birth").alias("year_birth")
)

dfSelected.printSchema()
root
 |-- id: integer (nullable = true)
 |-- year_birth: integer (nullable = true)
```

<ul>

<li id="4c08f87a-1051-434e-8332-e565477a5eab">

<p>위의 예시에서 df, dfSelected 는 각각 다른 DataFrame으로 불변이다&#46; 이 때, 물리적으로 실제 데이터가 복사되는 것은 아니다&#46; 물리적인 데이터는 여전히 Disk에 CSV파일로 존재하고 count() 등의 RDD 액션을 수행할 때, 데이터를 메모리로 읽어 처리한다&#46;</p>

</li>

</ul>

## 2&#46; <span className="notion-color-blue"><a href="https://phoenixnap.com/kb/rdd-vs-dataframe-vs-dataset">DataFrame vs DataSet vs SQL vs RDD</a></span>

<figure id="b663f399-faf5-4304-afc9-160629ba0a55" className="notion-figure">

<img src="/content/c9edaff4-1f8b-48aa-a092-730b932155fb/b663f399-faf5-4304-afc9-160629ba0a55.webp" alt="" loading="lazy" width="1662" height="742" />

</figure>

<ul>

<li id="2e11db04-91fe-45e6-ab08-92c2ab04d721">

<p>데이터를 탐색하거나, 빠르게 가공하고 싶다면 <strong>SQL API</strong>를 사용한다&#46;</p>

</li>

<li id="cafa446e-a2e0-42d3-9194-d7ed1c87c51b">

<p><strong>DataFrame</strong>은 untyped API로, SQL과 1&#58;1로 매핑된다&#46; DataFrame은 Dataset&#91;Row&#93; 즉, Row라는 타입의 Dataset이다&#46; </p>

</li>

<li id="d50f0e74-6754-4f01-b09f-69c7a5dfb2d4">

<p><strong>DataSet</strong>은 type-safe하며, lambda 등이 가능하다&#46; map, flatmap, filter 등 함수형 Collection API 일부를 사용할 수 있다&#46; <strong><span className="notion-color-blue">Encoder</span></strong>를 이용해 DataFrame을 Dataset&#91;T&#93;로 변경한다&#46; DataSet은 각 언어 구조에 따른 타입을 알 수 있다&#46; </p>

<span id="8fc3e6e6-340a-451f-8b38-3a63293a1d06"></span>

```kotlin
case class MarketingUser(userId: Int, 
                         yearBirth: Int)

# Encoder는 Serialization / Deserialization을 한다.
val dsMarketingUser = dfSelected.as[MarketingUser]

# dfSelected
org.apache.spark.sql.Dataset[org.apache.spark.sql.Row] = [id: int, yearBirth: int]

# dsMaretingUser
org.apache.spark.sql.Dataset[MarketingUser] = [userId: int, yearBirth: int]
```

</li>

</ul>

<ul>

<li id="f74b802c-af77-4d46-88b4-988cbbd6aab2">

<p>고도의 최적화 등 특별한 경우가 아니라면 낮은 수준의 API인 RDD를 사용하지 않는다&#46; 일정 규모에서는 머신에 비용을 투자하는 것이 고도의 최적화를 유지보수하는 것보다 저렴하다&#46; Public Cloud 환경에선 머신이 사람보다 구하기 쉽기 때문이다&#46;</p>

</li>

</ul>

#### Lazy Evaluation 장점

<ul>

<li id="30569171-0103-478e-b620-0fe38078fcb6">

<p>많은 데이터를 다룰 때, map(withColumn), filter(where)과 같은 함수를 호출할 때마다 즉시 연산된다면 데이터 로딩이 잦아져 네트워크 비용이 증가한다&#46;</p>

</li>

<li id="6d0ff87d-c215-4a65-b752-6e89c34ccf5f">

<p>map, filter 등을 통해 최적화가 가능한 로직이 존재할 경우 지연로딩함으로써 불필요한 연산을 피할 수 있다&#46;</p>

</li>

</ul>

## 5&#46; Partition

<figure id="b043b716-4565-4a19-baee-a25741bbb440" className="notion-figure">

<img src="/content/c9edaff4-1f8b-48aa-a092-730b932155fb/b043b716-4565-4a19-baee-a25741bbb440.webp" alt="" loading="lazy" width="1532" height="758" />

</figure>

<p id="dc1ee999-d9bc-47f8-afe6-39f77b6b27fd">데이터 시스템에서 Partition이란, 전체에서 나누어진 부분을 말한다&#46; 데이터가 수천억 건일 경우, 단일 머신에서 처리하기 어렵다&#46; 따라서 사용자는 DataFrame이라는 추상화된 API를 통해 데이터를 '하나'처럼 다루지만, Spark는 데이터를 분할해 Partition 단위로 데이터를 처리한다&#46;</p>
